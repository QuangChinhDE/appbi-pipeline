# Engine boundary

The most expensive mistakes in this repository are here. Read before editing.

## Who owns what

**AppBI owns** the product: auth, RBAC, tenancy, scheduling, retry policy,
audit, notification, the UI, and the *integration logic* in `app/adapters/`
that translates between product concepts and engine calls.

**Airbyte owns** ingestion execution: the connector protocol
(spec/check/discover/read/write), sync semantics, state and cursors, the
refresh protocol (`generation_id` / `minimum_generation_id` / `sync_id`), job
lifecycle and logs.

**dbt owns** transform execution: model compilation, DAG resolution, ref/source
semantics, materialization, artifacts (`manifest.json`, `run_results.json`),
tests and docs.

Do not reimplement any of the engine-owned list inside AppBI because calling
the engine is awkward. In particular: do not replace dbt's compilation or
lineage with hand-rolled SQL parsing, and do not re-derive sync state that
Airbyte already persists.

## The single boundary

`app/adapters/base.py::IntegrationEngineAdapter` is the only interface a domain
service may use. **Three** implementations satisfy it (`EngineType` in
`app/models/enums.py`, selected by `get_adapter()` in `adapters/registry.py`):

- `AIRBYTE_EMBEDDED` → `app.adapters.airbyte_protocol` — runs official connector
  images on the host Docker daemon over the Airbyte Protocol. Default.
- `AIRBYTE_API` → `app.adapters.airbyte_api` — delegates to an existing
  self-managed Airbyte.
- `SQL_DIRECT` → `app.adapters.sql_direct` — **not Airbyte at all.** Postgres to
  Postgres over a database connection, in-process: no connector images, no
  protocol, no spec/check/discover/read, no server-side connection object, no
  job service.

`sql_direct` is the load-bearing one for this rule. It exists precisely because
an interface with only Airbyte-shaped implementations behind it has not been
proven to abstract anything. **It is the test of whether your change respects
the boundary**: if a service you touched now assumes a connector image, a
catalog shape, a job id or any other Airbyte vocabulary, `sql_direct` cannot
satisfy it and the abstraction has quietly become an Airbyte façade. Before
calling an adapter change done, ask what `sql_direct` would do with it.

Note `compatibility.yaml` lists only the two Airbyte implementations — it
records what the *product* is certified to ship, and `sql_direct` is an
interface probe, not a shipped engine. Both facts are true; do not "fix" either
to match the other.

## Protected contracts

| File | What it is |
|---|---|
| `engine-lock.json` | Airbyte 0.59.1 + image digests. The last release that runs a sync under Docker Compose; 0.63+ has no Docker mode. |
| `connector-lock.json` | Pinned connector images, digests, spec hashes, certification status. Generated by `scripts/build-connector-lock.py`. |
| `compatibility.yaml` | What this product version was built and tested against, plus the record of what was actually run against a live Airbyte. Served by `GET /api/v1/admin/compatibility`. |
| `docker-compose*.yml` | Deployment topology per mode. |

Never hand-edit a lock file. Never bump a version, digest or
`tested_platform_versions` entry without a run that observed it — an entry in
`airbyte_api_certification` means someone watched it happen, not that the code
path exists.

## An engine change requires

- explicit task intent that says "change the engine"
- compatibility analysis against `compatibility.yaml` and `connector-lock.json`
- which deployments are affected (embedded / airbyte / transform / production / k8s)
- tests, including the adapter contract
- a rollback story

Engine modernization is never incidental cleanup.

## Compose variants are deployment contracts

`docker-compose.yml` is the base; `.airbyte`, `.embedded`, `.transform`,
`.storage`, `.egress`, `.production` are modes selected by `COMPOSE_FILE` in
`.env`. A change to one may affect every installation running that mode — volumes,
networks and egress rules especially. Treat it as cross-installation, not a YAML edit.

## Installers

`run.sh` and `run.ps1` are the product's installation and update path, and must
keep working for both a fresh checkout and an existing installation with
populated volumes. `run.sh` must stay compatible with Git Bash on Windows and a
POSIX shell on Ubuntu. Never regenerate or overwrite an existing secret from
these scripts: that invalidates every credential already encrypted with it.
